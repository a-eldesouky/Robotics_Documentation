# Probabilistic Roadmap Planning (PRM): A Practical Introduction for Robotics Path Planning

## 1. Introduction

Path planning is one of the core problems in robotics. A robot must find a valid path from a start configuration to a goal configuration while avoiding obstacles and respecting the constraints of its environment.

Classical graph-search methods such as BFS, DFS, Uniform Cost Search, and A* usually assume that the planning space has already been discretized into a grid or graph. This works well for simple two-dimensional problems, but it becomes expensive when the robot operates in a high-dimensional configuration space.

For example, a mobile robot moving on a flat floor may only need to reason about:

```text
x, y, θ
```

But a robotic arm may have six or more joints, and therefore a much larger configuration space:

```text
q = [q1, q2, q3, q4, q5, q6]
```

Fully discretizing such a space is often computationally impractical.

**Probabilistic Roadmap Planning**, commonly called **PRM**, solves this problem using random sampling. Instead of building the entire configuration space, PRM randomly samples valid configurations and connects them into a graph called a **roadmap**. This roadmap approximates the free space and can later be searched using graph algorithms such as A*. 

---

## 2. Core Concepts

### 2.1 Configuration Space

A robot configuration describes the robot’s complete state for planning purposes.

For a point robot in 2D:

```text
q = (x, y)
```

For a differential-drive robot:

```text
q = (x, y, θ)
```

For a robotic arm:

```text
q = (q1, q2, ..., qn)
```

The set of all possible configurations is called the **configuration space**, or **C-space**.

The C-space is divided into two main regions:

```text
C_free  = collision-free configurations
C_obs   = configurations that cause collision
```

The goal of path planning is to find a continuous path:

```text
τ : [0, 1] → C_free
```

such that:

```text
τ(0) = q_start
τ(1) = q_goal
```

In simple words, the robot must move from start to goal without entering collision.

---

### 2.2 Roadmap

A **roadmap** is a graph representation of the free space.

In PRM:

```text
Node  = collision-free configuration
Edge  = collision-free local motion between two nodes
```

The roadmap does not represent every possible configuration. Instead, it approximates connectivity in the free space.

If the roadmap is good enough, a graph search algorithm can find a sequence of connected nodes from start to goal.

---

### 2.3 Collision Checker

PRM does not need to explicitly construct the full C-space. It mainly needs a function that answers one question:

```text
Is this configuration collision-free?
```

For a 2D point robot, this may mean checking whether a point lies inside an obstacle.

For a real robot, collision checking may involve:

```text
Robot footprint
Obstacle geometry
Inflation radius
Robot body shape
Joint limits
Self-collision
Environment collision
```

The collision checker is one of the most important components of PRM.

---

### 2.4 Local Planner

The **local planner** checks whether two nearby configurations can be connected safely.

A simple local planner draws a straight line between two configurations and samples points along the line.

For two points:

```text
q_a = (x_a, y_a)
q_b = (x_b, y_b)
```

An interpolated point can be written as:

```text
q(t) = q_a + t(q_b - q_a),   0 ≤ t ≤ 1
```

If every sampled point along this edge is collision-free, the edge is accepted.

If any sampled point collides with an obstacle, the edge is rejected.

This step must be fast because PRM repeats it many times while building the roadmap.

---

## 3. Mathematical Foundations

### 3.1 Distance Metric

In a 2D educational implementation, the distance between two nodes is usually Euclidean distance:

```cpp
double distance(const Point& a, const Point& b)
{
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return std::sqrt(dx * dx + dy * dy);
}
```

Mathematically:

```text
d(a, b) = √((x_a - x_b)² + (y_a - y_b)²)
```

This distance is used for:

```text
Nearest-neighbor search
Edge cost calculation
A* heuristic
```

For more complex robots, the metric may include orientation, joint angles, weights, or robot-specific constraints.

Example for a 2D pose robot:

```text
q = (x, y, θ)
```

A distance metric may be:

```text
d(q1, q2) = wx √((x1 - x2)² + (y1 - y2)²) + wθ |θ1 - θ2|
```

The choice of metric strongly affects the roadmap quality.

---

### 3.2 Edge Cost

Each edge in the roadmap has a cost.

In the educational implementation, the edge cost is simply the Euclidean distance:

```cpp
double cost = distance(a, b);
```

This means A* will prefer shorter geometric paths.

In real robotics systems, edge cost may include:

```text
Distance
Traversal risk
Energy consumption
Time
Terrain difficulty
Clearance from obstacles
Turning cost
Dynamic feasibility
```

---

### 3.3 Probabilistic Completeness

PRM is **probabilistically complete**.

This means:

```text
If a valid path exists, the probability that PRM finds a path approaches 1 as the number of samples approaches infinity.
```

It does not mean PRM always finds a path quickly.

It means that with enough samples, the roadmap becomes more representative of the free space, and the chance of discovering a valid connection increases.

This is especially important in environments with narrow passages. If too few samples fall inside a narrow passage, PRM may fail even though a valid path exists.

---

## 4. System Model and Assumptions

The educational implementation uses a simplified 2D planning model.

The world is represented as a rectangular area:

```text
width × height
```

The robot is treated as a point.

Obstacles are axis-aligned rectangles:

```cpp
struct Obstacle
{
    double x_min, y_min;
    double x_max, y_max;
};
```

A point is considered in collision if it lies inside any obstacle.

This is a simplified model, but it is useful for learning the algorithm.

A practical robot implementation would usually replace this with:

```text
Occupancy grid collision checking
Costmap collision checking
Robot footprint checking
Inflated obstacle checking
SE(2) or SE(3) state representation
Motion constraints
```

For ROS 2 / Nav2-style systems, collision checking would normally be connected to a costmap instead of hardcoded rectangular obstacles.

---

## 5. PRM Algorithm

PRM has two main phases:

```text
1. Learning phase
2. Query phase
```

The learning phase builds the roadmap.

The query phase connects the start and goal to the roadmap and searches for a path.

---

### 5.1 Learning Phase

The learning phase builds a graph that approximates the free space.

The process is:

```text
1. Initialize an empty graph.
2. Generate random configurations.
3. Check whether each configuration is collision-free.
4. Add valid configurations as roadmap nodes.
5. Find nearby nodes.
6. Try to connect the new node to its neighbors.
7. Add collision-free edges to the graph.
```

Pseudocode:

```text
Initialize an empty graph G

For n iterations:

    Generate a random configuration q_rand

    If q_rand is collision-free:

        Add q_rand to graph G

        Find the k-nearest neighbors of q_rand

        For each neighbor q_near:

            Use the local planner to connect q_rand and q_near

            If the edge is collision-free:

                Add the edge to graph G
```

The result is a roadmap that captures possible movement through the free space.

---

### 5.2 Query Phase

After the roadmap is built, PRM can answer planning queries.

The query phase receives:

```text
q_start
q_goal
```

Then it does the following:

```text
1. Check that start and goal are collision-free.
2. Add start to the roadmap.
3. Connect start to nearby roadmap nodes.
4. Add goal to the roadmap.
5. Connect goal to nearby roadmap nodes.
6. Run graph search from start to goal.
```

If the roadmap connects start and goal through valid edges, A* can return a path.

The resulting path is a sequence of roadmap nodes:

```text
q_start → q1 → q2 → q3 → q_goal
```

This path may not be globally optimal, but it proves that a feasible path exists.

## 6. Educational C++ Implementation

The following implementation is designed for learning. It follows the same style as simple BFS, DFS, and A* examples: readable data structures, explicit logic, and clear separation between algorithm components.

```cpp
#include <iostream>
#include <vector>
#include <queue>
#include <cmath>
#include <random>
#include <limits>
#include <algorithm>

struct Point
{
    double x;
    double y;
};

struct Obstacle
{
    double x_min, y_min;
    double x_max, y_max;
};

struct Edge
{
    int to;
    double cost;
};

struct Node
{
    Point point;
    std::vector<Edge> neighbors;
};

double distance(const Point& a, const Point& b)
{
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return std::sqrt(dx * dx + dy * dy);
}

class PRMPlanner
{
public:
    PRMPlanner(
        double width,
        double height,
        int num_samples,
        int k_neighbors,
        double collision_step)
        : width_(width),
          height_(height),
          num_samples_(num_samples),
          k_neighbors_(k_neighbors),
          collision_step_(collision_step),
          gen_(std::random_device{}()),
          x_dist_(0.0, width),
          y_dist_(0.0, height)
    {
    }

    void addObstacle(const Obstacle& obstacle)
    {
        obstacles_.push_back(obstacle);
    }

    void buildRoadmap()
    {
        std::cout << "Building PRM roadmap...\n";

        for (int i = 0; i < num_samples_; ++i)
        {
            Point random_point = sampleRandomPoint();

            if (!isCollisionFree(random_point))
                continue;

            int new_node_id = addNode(random_point);

            auto nearest = findKNearestNeighbors(new_node_id);

            for (int neighbor_id : nearest)
            {
                Point a = nodes_[new_node_id].point;
                Point b = nodes_[neighbor_id].point;

                if (isEdgeCollisionFree(a, b))
                {
                    double cost = distance(a, b);

                    nodes_[new_node_id].neighbors.push_back({neighbor_id, cost});
                    nodes_[neighbor_id].neighbors.push_back({new_node_id, cost});
                }
            }
        }

        std::cout << "Roadmap built with " << nodes_.size() << " nodes.\n";
    }

    std::vector<Point> plan(const Point& start, const Point& goal)
    {
        if (!isCollisionFree(start) || !isCollisionFree(goal))
        {
            std::cout << "Start or goal is in collision.\n";
            return {};
        }

        int start_id = addNode(start);
        connectNodeToRoadmap(start_id);

        int goal_id = addNode(goal);
        connectNodeToRoadmap(goal_id);

        std::vector<int> node_path = aStar(start_id, goal_id);

        std::vector<Point> path;
        for (int id : node_path)
        {
            path.push_back(nodes_[id].point);
        }

        return path;
    }

private:
    double width_;
    double height_;
    int num_samples_;
    int k_neighbors_;
    double collision_step_;

    std::vector<Node> nodes_;
    std::vector<Obstacle> obstacles_;

    std::mt19937 gen_;
    std::uniform_real_distribution<double> x_dist_;
    std::uniform_real_distribution<double> y_dist_;

private:
    Point sampleRandomPoint()
    {
        return {x_dist_(gen_), y_dist_(gen_)};
    }

    int addNode(const Point& point)
    {
        nodes_.push_back({point, {}});
        return static_cast<int>(nodes_.size()) - 1;
    }

    bool isCollisionFree(const Point& p)
    {
        for (const auto& obs : obstacles_)
        {
            if (p.x >= obs.x_min && p.x <= obs.x_max &&
                p.y >= obs.y_min && p.y <= obs.y_max)
            {
                return false;
            }
        }

        return true;
    }

    bool isEdgeCollisionFree(const Point& a, const Point& b)
    {
        double edge_length = distance(a, b);
        int steps = std::max(1, static_cast<int>(edge_length / collision_step_));

        for (int i = 0; i <= steps; ++i)
        {
            double t = static_cast<double>(i) / steps;

            Point interpolated{
                a.x + t * (b.x - a.x),
                a.y + t * (b.y - a.y)
            };

            if (!isCollisionFree(interpolated))
                return false;
        }

        return true;
    }

    std::vector<int> findKNearestNeighbors(int node_id)
    {
        std::vector<std::pair<double, int>> distances;

        Point p = nodes_[node_id].point;

        for (int i = 0; i < static_cast<int>(nodes_.size()); ++i)
        {
            if (i == node_id)
                continue;

            double d = distance(p, nodes_[i].point);
            distances.push_back({d, i});
        }

        std::sort(distances.begin(), distances.end());

        std::vector<int> result;
        for (int i = 0; i < k_neighbors_ && i < static_cast<int>(distances.size()); ++i)
        {
            result.push_back(distances[i].second);
        }

        return result;
    }

    void connectNodeToRoadmap(int node_id)
    {
        auto nearest = findKNearestNeighbors(node_id);

        for (int neighbor_id : nearest)
        {
            Point a = nodes_[node_id].point;
            Point b = nodes_[neighbor_id].point;

            if (isEdgeCollisionFree(a, b))
            {
                double cost = distance(a, b);

                nodes_[node_id].neighbors.push_back({neighbor_id, cost});
                nodes_[neighbor_id].neighbors.push_back({node_id, cost});
            }
        }
    }

    std::vector<int> aStar(int start_id, int goal_id)
    {
        struct QueueNode
        {
            int id;
            double f_cost;

            bool operator>(const QueueNode& other) const
            {
                return f_cost > other.f_cost;
            }
        };

        std::priority_queue<
            QueueNode,
            std::vector<QueueNode>,
            std::greater<QueueNode>
        > open_list;

        std::vector<double> g_cost(nodes_.size(), std::numeric_limits<double>::infinity());
        std::vector<int> parent(nodes_.size(), -1);
        std::vector<bool> visited(nodes_.size(), false);

        g_cost[start_id] = 0.0;
        open_list.push({start_id, heuristic(start_id, goal_id)});

        while (!open_list.empty())
        {
            int current = open_list.top().id;
            open_list.pop();

            if (visited[current])
                continue;

            visited[current] = true;

            if (current == goal_id)
                return reconstructPath(parent, start_id, goal_id);

            for (const Edge& edge : nodes_[current].neighbors)
            {
                int neighbor = edge.to;
                double tentative_g = g_cost[current] + edge.cost;

                if (tentative_g < g_cost[neighbor])
                {
                    g_cost[neighbor] = tentative_g;
                    parent[neighbor] = current;

                    double f_cost = tentative_g + heuristic(neighbor, goal_id);
                    open_list.push({neighbor, f_cost});
                }
            }
        }

        std::cout << "No path found.\n";
        return {};
    }

    double heuristic(int node_id, int goal_id)
    {
        return distance(nodes_[node_id].point, nodes_[goal_id].point);
    }

    std::vector<int> reconstructPath(
        const std::vector<int>& parent,
        int start_id,
        int goal_id)
    {
        std::vector<int> path;
        int current = goal_id;

        while (current != -1)
        {
            path.push_back(current);

            if (current == start_id)
                break;

            current = parent[current];
        }

        std::reverse(path.begin(), path.end());
        return path;
    }
};

int main()
{
    PRMPlanner planner(
        100.0,   // map width
        100.0,   // map height
        300,     // number of random samples
        8,       // k nearest neighbors
        1.0      // collision checking step size
    );

    planner.addObstacle({30, 30, 45, 70});
    planner.addObstacle({60, 20, 75, 60});
    planner.addObstacle({20, 80, 80, 90});

    planner.buildRoadmap();

    Point start{10, 10};
    Point goal{90, 80};

    std::vector<Point> path = planner.plan(start, goal);

    if (!path.empty())
    {
        std::cout << "\nFound path:\n";

        for (const auto& p : path)
        {
            std::cout << "(" << p.x << ", " << p.y << ")\n";
        }
    }

    return 0;
}
```

Compile and run:

```bash
g++ prm.cpp -o prm -std=c++17
./prm
```

## 7. Code Explanation

### 7.1 Point

```cpp
struct Point
{
    double x;
    double y;
};
```

This represents a 2D robot configuration.

In this simplified planner, the robot has no orientation and no footprint. It is treated as a point moving in a 2D world.

---

### 7.2 Obstacle

```cpp
struct Obstacle
{
    double x_min, y_min;
    double x_max, y_max;
};
```

Each obstacle is represented as an axis-aligned rectangle.

A point is in collision if:

```text
x_min ≤ x ≤ x_max
y_min ≤ y ≤ y_max
```

This is simple but useful for understanding collision checking.

---

### 7.3 Edge

```cpp
struct Edge
{
    int to;
    double cost;
};
```

An edge connects one roadmap node to another.

The `to` field stores the neighbor node index.

The `cost` field stores the cost of moving along that edge.

---

### 7.4 Node

```cpp
struct Node
{
    Point point;
    std::vector<Edge> neighbors;
};
```

A node contains:

```text
A sampled collision-free point
A list of connected neighbors
```

Together, all nodes form the roadmap graph.

---

### 7.5 PRMPlanner Class

The `PRMPlanner` class contains the whole planning pipeline:

```text
Sampling
Collision checking
Roadmap construction
Neighbor search
Local planning
A* graph search
Path reconstruction
```

This makes the implementation close to how robotics planners are usually organized: each part of the algorithm has a clear responsibility.

---

### 7.6 buildRoadmap()

```cpp
void buildRoadmap()
```

This function implements the PRM learning phase.

It repeatedly samples random points and checks whether they are collision-free.

If a point is valid, it is added to the graph.

Then the planner finds its nearest neighbors and attempts to connect it to them.

If the edge between the new node and a neighbor is collision-free, the edge is added in both directions:

```cpp
nodes_[new_node_id].neighbors.push_back({neighbor_id, cost});
nodes_[neighbor_id].neighbors.push_back({new_node_id, cost});
```

This makes the roadmap an undirected graph.

---

### 7.7 plan()

```cpp
std::vector<Point> plan(const Point& start, const Point& goal)
```

This function implements the query phase.

It checks whether start and goal are valid, then adds them to the graph.

After that, it connects both to nearby roadmap nodes and runs A*.

The returned result is a list of 2D points representing the path.

---

### 7.8 isCollisionFree()

```cpp
bool isCollisionFree(const Point& p)
```

This checks whether a sampled point lies inside any obstacle.

If the point is inside an obstacle, the function returns `false`.

Otherwise, it returns `true`.

In a real robot, this function would likely use a costmap or collision-checking library.

---

### 7.9 isEdgeCollisionFree()

```cpp
bool isEdgeCollisionFree(const Point& a, const Point& b)
```

This is the local planner.

It interpolates between two points and checks intermediate samples for collision.

If any intermediate sample is in collision, the edge is rejected.

The important parameter here is:

```cpp
collision_step_
```

A small step gives safer checking but increases computation.

A large step is faster but may miss thin obstacles.

---

### 7.10 findKNearestNeighbors()

```cpp
std::vector<int> findKNearestNeighbors(int node_id)
```

This function finds the closest roadmap nodes to the given node.

The educational implementation uses brute-force search:

```text
Compare the node against every other node
Sort by distance
Return the closest k nodes
```

This is simple and readable.

For large graphs, a better implementation would use a k-d tree or another nearest-neighbor data structure.

---

### 7.11 aStar()

```cpp
std::vector<int> aStar(int start_id, int goal_id)
```

This searches the roadmap graph.

It uses:

```text
g_cost = cost from start to current node
h_cost = estimated cost from current node to goal
f_cost = g_cost + h_cost
```

The heuristic is Euclidean distance:

```cpp
double heuristic(int node_id, int goal_id)
{
    return distance(nodes_[node_id].point, nodes_[goal_id].point);
}
```

Because edge costs are also Euclidean distances, this heuristic is admissible in the simplified 2D case.

---

## 8. Parameters and Tuning

### 8.1 Number of Samples

```cpp
num_samples_
```

This controls how many random configurations are generated during the learning phase.

Increasing this value creates a denser roadmap.

Benefits:

```text
Higher chance of finding a path
Better coverage of free space
Better handling of narrow passages
```

Costs:

```text
More computation
More memory
More collision checks
Slower roadmap construction
```

A low number of samples may cause failure even when a valid path exists.

---

### 8.2 Number of Neighbors

```cpp
k_neighbors_
```

This controls how many nearby nodes each new sample tries to connect to.

A higher value makes the graph more connected.

Benefits:

```text
Better chance of connecting separate free-space regions
More possible paths
Potentially shorter paths
```

Costs:

```text
More edge collision checks
More graph edges
Slower construction
```

If `k_neighbors_` is too small, the graph may become disconnected.

If it is too large, roadmap construction becomes expensive.

---

### 8.3 Collision Checking Step

```cpp
collision_step_
```

This controls the spacing between samples along an edge.

A smaller value checks edges more carefully.

Benefits:

```text
Less chance of missing obstacles
Safer edges
Better geometric validity
```

Costs:

```text
More collision checks per edge
Slower local planning
```

A large value may allow invalid edges to pass through thin obstacles.

---

### 8.4 Map Size

```cpp
width_
height_
```

These define the sampling bounds.

Random samples are generated inside:

```text
0 ≤ x ≤ width
0 ≤ y ≤ height
```

In real applications, these bounds should match the known planning area.

Bad bounds can waste samples in irrelevant areas or prevent sampling in important regions.

---

### 8.5 Neighbor Strategy

The example uses k-nearest neighbors.

Another common strategy is radius-based connection:

```text
Connect to all nodes within radius r
```

k-nearest is easier to control because every node attempts the same number of connections.

Radius-based connection adapts naturally to local density but may create too many or too few edges depending on sampling distribution.

## 9. Edge Cases and Limitations

### 9.1 Start or Goal in Collision

If the start or goal lies inside an obstacle, planning immediately fails.

```cpp
if (!isCollisionFree(start) || !isCollisionFree(goal))
{
    std::cout << "Start or goal is in collision.\n";
    return {};
}
```

This is necessary because PRM only searches through valid configurations.

---

### 9.2 Disconnected Roadmap

PRM may fail if the graph is not connected.

This can happen when:

```text
Too few samples are used
k_neighbors is too small
Obstacles divide the space into difficult regions
Narrow passages are under-sampled
```

The planner may print:

```text
No path found.
```

even though a real path exists.

This is a sampling failure, not necessarily proof that the environment is impossible.

---

### 9.3 Narrow Passages

Narrow passages are one of the classic weaknesses of PRM.

Because PRM samples randomly, it may place very few nodes inside narrow regions.

Without enough nodes in these regions, the roadmap cannot represent the valid path.

Possible improvements include:

```text
Increasing the number of samples
Using obstacle-biased sampling
Using bridge sampling
Using Gaussian sampling
Increasing connection attempts near difficult regions
```

---

### 9.4 Dynamic Obstacles

PRM is best suited for static or mostly static environments.

If obstacles move frequently, the roadmap may become invalid.

In such environments, PRM loses one of its main advantages: roadmap reuse.

For highly dynamic environments, planners such as RRT, RRT*, D*, Anytime D*, or local reactive planners may be more suitable.

---

### 9.5 Non-Holonomic Robots

The educational implementation connects nodes using straight lines.

This is acceptable for a point robot or a holonomic robot, but it may be invalid for robots with motion constraints.

For example, a car-like robot cannot move sideways and has a minimum turning radius.

For such systems, the local planner must respect vehicle kinematics.

Possible local planners include:

```text
Dubins paths
Reeds-Shepp paths
State lattice primitives
Kinodynamic local planners
```

---

### 9.6 Path Quality

PRM finds a feasible graph path, but the result may be jerky or unnecessarily long.

The graph path is only as good as the samples and edges in the roadmap.

Post-processing is often applied, such as:

```text
Path shortcutting
Path smoothing
Spline fitting
Trajectory optimization
Time parameterization
```

---

## 10. Practical Engineering Insights

### 10.1 PRM Is a Multi-Query Planner

PRM is called a **multi-query planner** because the roadmap can be reused.

The expensive part is the learning phase.

Once the roadmap is built, many different start-goal queries can be solved quickly by connecting the start and goal to the graph and running A*.

This makes PRM useful for:

```text
Static maps
Known workspaces
Repeated planning queries
Robot arms in fixed environments
Warehouse-like environments
```

---

### 10.2 PRM vs A*

A* searches an existing graph.

PRM builds the graph first, then uses A*.

So PRM is not a replacement for A*. Instead, PRM can generate the graph that A* searches.

The relationship is:

```text
PRM  → builds roadmap graph
A*   → searches roadmap graph
```

In grid-based planning, the graph is usually the grid.

In PRM, the graph is randomly sampled from free space.

---

### 10.3 PRM vs RRT

PRM is multi-query.

RRT is usually single-query.

PRM builds a roadmap that tries to represent the overall free space.

RRT grows a tree from the start toward unexplored regions, usually focusing more directly on a specific query.

A useful comparison:

| Planner | Type                                 | Best For                                   |
| ------- | ------------------------------------ | ------------------------------------------ |
| PRM     | Multi-query                          | Static environments with repeated queries  |
| RRT     | Single-query                         | Faster planning for one start-goal problem |
| RRT*    | Single-query, asymptotically optimal | Better path quality over time              |
| A*      | Graph search                         | Searching a known graph or grid            |

---

### 10.4 Complexity Intuition

If PRM uses:

```text
n = number of samples
k = number of neighbors
```

Then the number of local planner checks is approximately:

```text
n × k
```

This is why the local planner must be efficient.

The brute-force nearest-neighbor search in the educational implementation is simple but not optimal.

For each new node, it compares against all existing nodes, so the cost grows significantly as the roadmap becomes large.

Production systems often use:

```text
k-d trees
Ball trees
Approximate nearest-neighbor search
Spatial hashing
```

## 11. Improved Educational Notes

The implementation is intentionally simple, but there is one important safety detail in the edge checker.

A naive implementation might write:

```cpp
int steps = static_cast<int>(edge_length / collision_step_);
```

Then compute:

```cpp
double t = static_cast<double>(i) / steps;
```

If the edge is shorter than `collision_step_`, `steps` could become zero, causing division by zero.

The improved version avoids this:

```cpp
int steps = std::max(1, static_cast<int>(edge_length / collision_step_));
```

This ensures that at least one interpolation segment is checked.

This kind of detail matters in robotics code because rare edge cases can cause runtime failures.

## 12. Summary of the Full PRM Pipeline

The complete PRM process can be summarized as:

```text
1. Randomly sample configurations.
2. Reject samples that are in collision.
3. Add valid samples as graph nodes.
4. Find nearby nodes.
5. Use a local planner to test edges.
6. Add collision-free edges to the roadmap.
7. Add start and goal to the roadmap.
8. Connect start and goal to nearby nodes.
9. Run A* on the roadmap.
10. Return the resulting path.
```

Compactly:

```text
PRM = sample free space → connect neighbors → build roadmap → query with graph search
```

## 13. Conclusion

Probabilistic Roadmap Planning is a powerful sample-based planning method for robotics. Its main idea is to avoid full configuration-space discretization by randomly sampling collision-free configurations and connecting them into a reusable graph.

PRM is especially effective when the environment is static or only mildly changing, because the roadmap can be reused for many planning queries. This makes it a strong choice for multi-query planning problems such as robotic manipulation in fixed workcells or navigation in known environments.

Its main weaknesses are sensitivity to sampling density, difficulty with narrow passages, and reduced usefulness in dynamic environments. The quality of PRM depends heavily on the number of samples, neighbor selection strategy, collision checker, and local planner.

From an implementation perspective, PRM combines several important robotics planning ideas:

```text
Random sampling
Collision checking
Local planning
Graph construction
Nearest-neighbor search
A* graph search
```

Understanding PRM is valuable because it forms the foundation for many advanced sampling-based planners and provides a clear bridge between classical graph search and modern high-dimensional robot motion planning.
