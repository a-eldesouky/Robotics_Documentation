# A Unified Mental Model for Path Planning, Motion Planning, Trajectory Generation, and Control

## 1. Introduction

Path planning and motion planning are central problems in robotics and autonomous driving. They answer a deceptively simple question:

> How should an autonomous system move safely, efficiently, and predictably from its current state to a desired goal?

The confusion often comes from terminology. In robotics, especially ROS-based navigation systems, planning and execution are usually separated into clear software modules: a global planner computes a path, a controller follows it, and recovery behaviors handle failure. In autonomous driving, many of these responsibilities are grouped under the broader term **motion planning**, because route choice, behavior, trajectory generation, obstacle avoidance, speed planning, and comfort are tightly coupled.

The key insight is this:

> Path planning is about where to go.
> Motion planning is about how to move safely and feasibly.
> Trajectory generation adds time, velocity, and smoothness.
> Control executes the planned motion on the real robot or vehicle.

This article builds a unified mental model that connects robotics stacks such as ROS 2 Nav2 with autonomous driving stacks such as those used in Waymo-style, Apollo-style, or Autoware-style systems.

---

## 2. Core Concepts

### Path Planning

Path planning computes a collision-free geometric route from a start state to a goal state.

A path usually contains spatial information:

```text
(x, y)
or
(x, y, yaw)
```

It does not necessarily include time, velocity, acceleration, jerk, or actuator commands.

Common path planning algorithms include:

```text
A*
Dijkstra
RRT
RRT*
PRM
Hybrid A*
```

In mobile robotics, path planning often means:

```text
map + start + goal → collision-free path
```

For example, in a warehouse robot, a global planner may compute a path through an occupancy grid from the current pose to a shelf location.

---

### Motion Planning

Motion planning is broader. It computes feasible motion while considering obstacles, kinematics, dynamics, safety, and sometimes time.

A motion plan may include:

```text
x(t), y(t), yaw(t), velocity(t), acceleration(t), curvature(t)
```

In autonomous driving, motion planning often includes:

```text
behavior selection
local path generation
dynamic obstacle avoidance
speed planning
trajectory optimization
comfort constraints
safety checking
```

So while path planning can be part of motion planning, it is not the whole problem.

A* alone is not a complete autonomous driving planner. It may produce a route, but it does not decide whether to yield, overtake, stop for a pedestrian, or generate a dynamically feasible speed profile.

---

### Trajectory Generation

Trajectory generation converts a path or maneuver into a smooth, time-parameterized reference.

A path may look like this:

```text
[(x1, y1), (x2, y2), (x3, y3)]
```

A trajectory looks like this:

```text
[(x1, y1, yaw1, v1, t1),
 (x2, y2, yaw2, v2, t2),
 (x3, y3, yaw3, v3, t3)]
```

Trajectory generation answers:

> Where should the robot be at each moment in time?

It often uses:

```text
splines
Bezier curves
polynomials
minimum-jerk trajectories
Frenet-frame trajectories
velocity profiles
trajectory optimization
```

A trajectory must be smooth enough for the controller and feasible enough for the robot or vehicle.

---

### Control

Control executes the desired trajectory.

It answers:

> What command should be sent to the robot right now?

For a differential-drive robot, the output may be:

```text
linear velocity
angular velocity
```

For a car-like vehicle, the output may be:

```text
steering angle
throttle
brake
```

Common control methods include:

```text
PID
Pure Pursuit
Stanley Controller
LQR
MPC
Regulated Pure Pursuit
```

A controller does not usually decide the mission. It tracks a reference generated by the planning stack.

## 3. Why Robotics and Autonomous Driving Use Different Terminology

The terminology differs because the system boundaries are different.

In many robotics systems, especially ROS/Nav2-style navigation, the architecture is modular:

```text
Global Planner → Controller → Recovery Behaviors
```

The planner computes a path. The controller follows it. The behavior tree coordinates execution and recovery.

In autonomous driving, the middle of the stack is more coupled:

```text
Routing → Behavior Planning → Motion Planning → Trajectory → Control
```

A car cannot simply follow a geometric path. It must reason about traffic rules, lane changes, dynamic objects, predicted motion, safety margins, comfort, acceleration limits, steering limits, and legal behavior.

Therefore, autonomous driving teams often use **motion planning** to describe a larger block that includes behavior, path, speed, and trajectory generation.

The important senior-level distinction is:

```text
Robotics terminology often follows software modules.
Autonomous driving terminology often follows driving responsibilities.
```

The underlying concepts are similar, but the grouping is different.

## 4. Unified Autonomous Stack

A full autonomous system can be understood as the following pipeline:

```text
Sensors
  ↓
Perception
  ↓
Prediction
  ↓
Planning
  ↓
Control
  ↓
Actuation
```

Expanded:

```text
Camera / LiDAR / Radar / IMU / GPS
        ↓
Localization + Mapping
        ↓
Perception
        ↓
Prediction
        ↓
Global Planning / Routing
        ↓
Behavior Planning
        ↓
Local Motion Planning
        ↓
Trajectory Generation
        ↓
Control
        ↓
Vehicle or Robot
```

Each layer has a different responsibility.

## 5. Global Planning

### Responsibility

Global planning computes the high-level route from the current position to the goal.

In robotics, this may be a path through an occupancy grid.

In autonomous driving, it may be a lane-level route through an HD map.

### Inputs

```text
current pose
goal pose
map
road graph or occupancy grid
mission constraints
blocked areas
costmap
```

### Outputs

For mobile robots:

```text
global path as a list of poses
```

For autonomous vehicles:

```text
route corridor
lane sequence
road segment sequence
```

### Algorithms

Common algorithms include:

```text
Dijkstra
A*
Theta*
Jump Point Search
Hybrid A*
lane graph search
road network search
```

### Practical Constraints

Global planning usually runs slower than local planning. It is responsible for large-scale route correctness, not immediate obstacle avoidance.

It must handle:

```text
map changes
blocked roads
unreachable goals
route cost
mission constraints
large graph search
```

In Nav2, this corresponds mainly to the **Planner Server**. In autonomous driving, this is closer to **routing**.

---

## 6. Behavior Planning

### Responsibility

Behavior planning chooses the semantic driving or navigation decision.

It answers:

```text
Should I stop?
Should I yield?
Should I follow?
Should I overtake?
Should I change lane?
Should I wait?
Should I pull over?
```

This layer is especially important in autonomous driving.

### Inputs

```text
global route
current vehicle state
traffic rules
lane information
obstacles
predicted object trajectories
traffic lights
right-of-way rules
mission state
```

### Outputs

```text
selected maneuver
target lane
desired speed policy
stop/yield/follow decision
safe gap selection
```

Example behavior decisions:

```text
FOLLOW_LANE
STOP_FOR_PEDESTRIAN
YIELD_AT_INTERSECTION
CHANGE_LANE_LEFT
NUDGE_AROUND_OBSTACLE
PULL_OVER
```

### Algorithms

Behavior planning may use:

```text
finite state machines
behavior trees
rule-based systems
cost-based decision making
POMDP-style reasoning
learning-based policies
```

### Practical Constraints

Behavior planning is where many real-world autonomy failures occur.

It must handle:

```text
uncertainty
social behavior
deadlocks
right-of-way
traffic rules
safety margins
fallback behavior
explainability
```

A perfect trajectory generator cannot compensate for a poor behavior decision. If the behavior planner chooses an unsafe lane change, the downstream planner may have no good solution.

---

## 7. Local / Motion Planning

### Responsibility

Local motion planning generates a feasible short-horizon motion that satisfies the behavior decision.

It answers:

> Given the selected maneuver, what motion should the robot or vehicle execute now?

### Inputs

```text
behavior decision
route corridor
local map
costmap
detected obstacles
predicted object motion
current vehicle state
vehicle model
dynamic limits
```

### Outputs

```text
candidate paths
selected local path
spatio-temporal trajectory
speed profile
```

### Algorithms

Common local or motion planning methods include:

```text
Hybrid A*
RRT / RRT*
state lattice planners
Frenet-frame planners
trajectory rollouts
elastic band methods
optimization-based planners
MPC-based planning
```

### Practical Constraints

Local planning is usually time-critical.

It must satisfy:

```text
collision avoidance
kinematic feasibility
dynamic feasibility
comfort
smoothness
low latency
replanning stability
prediction uncertainty
```

This is where autonomous driving becomes much more complex than simple grid-based robotics navigation. The planner must reason not only about where obstacles are now, but where they will be in the future.

---

## 8. Trajectory Generation

### Responsibility

Trajectory generation converts the selected path or maneuver into a smooth reference over time.

It answers:

> Where should the robot be at each future time step, and with what velocity and acceleration?

### Inputs

```text
local path
current state
target speed
behavior decision
obstacle constraints
road boundaries
vehicle limits
comfort constraints
```

### Outputs

```text
x(t)
y(t)
yaw(t)
velocity(t)
acceleration(t)
jerk(t)
curvature(t)
```

### Methods

Trajectory generation may use:

```text
cubic polynomials
quintic polynomials
splines
Bezier curves
clothoids
minimum-jerk trajectories
Frenet s-l trajectories
path-velocity decomposition
spatio-temporal optimization
```

### Practical Constraints

A valid trajectory must respect:

```text
maximum velocity
maximum acceleration
maximum jerk
curvature limits
steering limits
steering rate limits
collision constraints
comfort constraints
```

A path can be geometrically valid but temporally unsafe.

For example, a path may avoid a pedestrian’s current position, but the timed trajectory may reach the crossing at the same moment as the pedestrian. This is why autonomous driving planning must reason in space and time, not just geometry.

---

## 9. Control

### Responsibility

Control tracks the generated trajectory and sends commands to the physical platform.

It answers:

> What actuator command should be applied now?

### Inputs

```text
current state
reference trajectory
tracking error
vehicle model
actuator limits
odometry
localization feedback
```

### Outputs

For mobile robots:

```text
cmd_vel
linear velocity
angular velocity
```

For cars:

```text
steering
throttle
brake
gear
```

### Algorithms

Common controllers include:

```text
PID
Pure Pursuit
Stanley
LQR
MPC
feedforward + feedback control
```

### Practical Constraints

Control must handle:

```text
latency
tracking error
actuator delay
wheel slip
tire dynamics
friction
slope
disturbances
saturation
stability
```

A controller may be simple or complex depending on the platform. A warehouse robot may use a velocity controller. A high-speed autonomous car may require model-based control with steering, throttle, and brake constraints.

---

## 10. Where Common Algorithms Fit

A useful mapping is:

```text
A*, Dijkstra
→ global graph/path planning

Hybrid A*
→ kinematically feasible path planning, especially parking or constrained spaces

RRT, RRT*
→ sampling-based planning in continuous or high-dimensional spaces

State lattice
→ structured motion planning using precomputed feasible motion primitives

Frenet planners
→ road/lane-based local trajectory generation

Optimization-based planners
→ smoothing, constraint satisfaction, obstacle avoidance, comfort optimization

Pure Pursuit, Stanley
→ path/trajectory tracking control

MPC
→ either control or local motion planning, depending on formulation
```

The important nuance is MPC.

If MPC tracks a reference trajectory and outputs steering/throttle/brake, it is mainly a controller.

If MPC optimizes future motion while considering obstacles and constraints, it becomes a local motion planner or trajectory optimizer.

## 11. Robotics Stack vs Autonomous Driving Stack

### ROS 2 Nav2-Style Architecture

A typical Nav2-style system looks like:

```text
Map / Costmap
   ↓
Global Planner
   ↓
Controller
   ↓
cmd_vel
```

With a behavior tree supervising:

```text
NavigateToPose
  ├── compute path
  ├── follow path
  ├── recover
  └── replan if needed
```

The main conceptual modules are:

```text
Planner Server
→ computes global path

Controller Server
→ follows path and may perform local obstacle handling

Behavior Server
→ recovery behaviors

BT Navigator
→ task orchestration and execution logic
```

This architecture is modular and reusable across many robot types.

It works well for:

```text
indoor robots
warehouse robots
service robots
differential-drive robots
low-speed navigation
occupancy-grid maps
```

---

### Autonomous Driving Architecture

A typical autonomous driving stack looks like:

```text
Routing
  ↓
Behavior Planning
  ↓
Motion Planning
  ↓
Trajectory Generation
  ↓
Control
```

The planning system must handle:

```text
HD maps
lane graphs
traffic rules
dynamic obstacles
prediction
lane changes
merging
yielding
stopping
comfort
vehicle dynamics
legal driving behavior
```

The planning problem is more coupled because behavior, path, and speed cannot be fully separated.

A lane change is not just a geometric path. It requires:

```text
gap selection
prediction
traffic rule checking
speed planning
safety validation
trajectory generation
control feasibility
```

---

### What Is Actually Different?

Some differences are only naming:

```text
global planner ≈ routing
local planner ≈ motion planner
trajectory tracker ≈ controller
```

But some differences are real:

```text
AVs require stronger prediction integration
AVs use lane-level and HD-map reasoning
AVs plan in space-time
AVs handle higher speeds
AVs require comfort and legality
AVs reason about interactive agents
AVs separate behavior planning more explicitly
```

The unified view is:

```text
Robotics often emphasizes modular software separation.
Autonomous driving emphasizes coupled driving decisions.
```

## 12. Concrete Scenario: City Driving Around an Obstacle

Consider a car driving in a city. It detects a stopped vehicle partially blocking its lane.

### Step 1: Perception

The perception system processes sensor data:

```text
camera
LiDAR
radar
HD map
localization
```

It detects:

```text
stopped vehicle ahead
lane boundaries
free space
traffic lights
nearby cars
pedestrians
```

Output:

```text
Obstacle at 35 meters ahead, partially blocking ego lane.
```

---

### Step 2: Prediction

Prediction estimates future motion of dynamic agents.

For the stopped vehicle:

```text
velocity ≈ 0
predicted to remain stationary
```

For nearby vehicles:

```text
future position of left-lane car
future position of rear vehicle
possible pedestrian motion
```

Output:

```text
Left lane has a vehicle approaching from behind.
Obstacle is likely stationary.
Right side is blocked by curb.
```

---

### Step 3: Global Planning / Routing

The route remains valid.

The car still needs to continue on the current road toward the destination.

Output:

```text
Continue along current route corridor.
```

No large-scale route change is needed.

---

### Step 4: Behavior Planning

The behavior planner evaluates possible decisions:

```text
stop behind obstacle
wait for gap
change lane left
nudge around obstacle
reroute
```

It checks:

```text
lane markings
traffic rules
left-lane availability
rear vehicle speed
distance to intersection
safety gap
```

Possible decision:

```text
Wait, then change lane left when safe.
```

---

### Step 5: Local Motion Planning

The motion planner generates candidate motions:

```text
Trajectory A: slow down and merge behind left-lane vehicle
Trajectory B: accelerate and merge ahead
Trajectory C: stop behind obstacle
Trajectory D: nudge left slightly
```

Each candidate is evaluated for:

```text
collision risk
comfort
curvature
acceleration
jerk
lane boundary violation
time-to-collision
dynamic feasibility
```

The selected motion may be:

```text
slow down slightly
merge left behind the approaching vehicle
pass the stopped obstacle
continue in the target lane
```

---

### Step 6: Trajectory Generation

The selected motion is converted into a timed trajectory:

```text
t = 0.0 s → x, y, yaw, v = 10.0 m/s
t = 1.0 s → x, y, yaw, v = 9.5 m/s
t = 2.0 s → x, y, yaw, v = 9.0 m/s
t = 3.0 s → x, y, yaw, v = 9.2 m/s
```

The trajectory respects:

```text
maximum lateral acceleration
maximum jerk
steering rate limit
safe distance
collision-free space-time corridor
```

---

### Step 7: Control

The controller tracks the reference trajectory.

It computes:

```text
steering
throttle
brake
```

The controller compensates for:

```text
tracking error
actuator delay
road friction
localization noise
model mismatch
```

---

### Step 8: Continuous Replanning

The system continuously repeats the loop.

If a pedestrian suddenly appears:

```text
perception updates obstacle list
prediction estimates pedestrian motion
behavior switches to STOP or YIELD
motion planner generates braking trajectory
controller executes deceleration
```

This is why autonomy is not a one-shot planning problem. It is a closed-loop system.

---

## 13. Edge Cases and Limitations

### Geometric Validity Does Not Guarantee Executability

A path may avoid obstacles but still be impossible to follow due to:

```text
turning radius
steering limits
velocity constraints
acceleration limits
jerk limits
vehicle dynamics
```

This is why car-like systems often need Hybrid A*, lattice planners, or optimization-based methods.

---

### Static Planning Does Not Handle Dynamic Risk

A static path may be collision-free now but unsafe in two seconds.

Dynamic systems need prediction and time-aware planning.

---

### Behavior Mistakes Are Expensive

If the behavior planner chooses the wrong maneuver, downstream modules may fail.

Examples:

```text
choosing to merge into an unsafe gap
stopping unnecessarily in traffic
failing to yield
getting stuck in deadlock
```

Senior engineers must reason about behavior and planning together.

---

### Local Minima and Oscillation

Local planners can oscillate when multiple options have similar cost.

Examples:

```text
left/right obstacle avoidance switching
stop/go hesitation
lane-change abort loops
```

Solutions include:

```text
hysteresis
state machines
behavior commitment
cost smoothing
trajectory consistency penalties
```

---

### Replanning Can Create Instability

Frequent replanning can cause jerky motion if each new plan differs significantly from the previous one.

Practical systems often enforce:

```text
trajectory continuity
warm-starting
commitment windows
smooth cost functions
previous trajectory reuse
```

---

## 14. Parameters and Tuning

Important planning and control parameters include:

### Cost Weights

Used in optimization and candidate selection:

```text
obstacle cost
lane deviation cost
comfort cost
speed cost
curvature cost
jerk cost
progress cost
```

Increasing obstacle cost makes the system more conservative. Increasing progress cost makes it more aggressive.

---

### Safety Margins

```text
minimum distance to obstacles
time-to-collision threshold
following distance
lateral clearance
```

Larger margins improve safety but may reduce efficiency or cause unnecessary stops.

---

### Dynamic Limits

```text
max velocity
max acceleration
max deceleration
max jerk
max curvature
max steering angle
max steering rate
```

These limits must match the real platform. Unrealistic limits create trajectories that the controller cannot track.

---

### Replanning Rate

Planning frequency affects responsiveness.

Low frequency may make the system slow to react. Very high frequency may waste compute and cause unstable plan switching.

Typical architecture:

```text
global planning: low frequency or event-triggered
behavior planning: medium frequency
local planning: medium/high frequency
control: high frequency
```

---

### Controller Gains

Controller tuning affects:

```text
tracking accuracy
oscillation
overshoot
smoothness
stability
```

Aggressive gains reduce tracking error but may cause oscillation. Conservative gains are smoother but may lag behind the trajectory.

---

## 15. Practical Engineering Insights

### The Output Representation Defines the Module

A strong way to classify systems is by output:

```text
Route → global planning
Maneuver → behavior planning
Path → path planning
Trajectory → trajectory generation / motion planning
Actuator command → control
```

This avoids terminology confusion.

---

### Planning Is Not Just an Algorithm

A real planner is not simply “A*” or “RRT”.

A production planning system includes:

```text
state estimation
map interface
cost functions
collision checking
prediction interface
fallback handling
debug tools
safety validation
runtime monitoring
```

The algorithm is only one part of the system.

---

### Control Cannot Fix Bad Planning

If the trajectory is dynamically infeasible, the controller will fail.

Good planning must produce trajectories that are:

```text
trackable
smooth
safe
within actuator limits
consistent across cycles
```

---

### Prediction and Planning Are Coupled

In autonomous driving, planning depends heavily on prediction.

A vehicle cannot decide whether to merge without estimating how surrounding vehicles will move.

This is one of the biggest differences between simple mobile robot navigation and autonomous driving.

---

### Senior-Level Thinking Is About Interfaces

A senior engineer should be able to describe:

```text
what each module owns
what each module receives
what each module outputs
what assumptions each module makes
how failure propagates
how safety is enforced
```

This is more valuable in an interview than only naming algorithms.

---

## 16. Interview-Level Summary

A strong senior interview answer could be:

> I separate planning by responsibility and output representation. Global planning finds a route or corridor. Behavior planning chooses the semantic maneuver, such as stop, yield, follow, or change lane. Motion planning generates a feasible local motion considering obstacles, prediction, vehicle constraints, and comfort. Trajectory generation converts that motion into a smooth time-parameterized reference. Control tracks that reference using steering, throttle, brake, or velocity commands. In ROS/Nav2, these responsibilities are separated into planner, controller, behavior tree, and recovery modules. In autonomous driving, they are often grouped under motion planning because behavior, path, speed, prediction, and trajectory feasibility are tightly coupled.

Common misconceptions to avoid:

```text
A* is not a complete motion planning system.
Hybrid A* does not solve behavior planning.
Trajectory generation is not control.
A path is not necessarily a trajectory.
A collision-free path is not necessarily dynamically feasible.
A controller cannot compensate for unsafe planning.
```

```text
Route → Decision → Motion → Command
```

Expanded:

```text

Behavior Planning

Motion Planning
"What feasible motion realizes that decision?"

Trajectory Generation
"Where should I be at each time?"

```

## Conclusion

Path planning, motion planning, trajectory generation, and control are not competing concepts. They are layers of the same autonomy pipeline.

The terminology changes between robotics and autonomous driving because the software architecture and problem complexity differ. Robotics stacks often separate planning and execution into modular components. Autonomous driving stacks often group behavior, path, speed, and trajectory generation under motion planning because these decisions are tightly coupled by traffic, prediction, dynamics, and safety.

The most important mental model is:

> Planning decides what motion should happen.
> Trajectory generation makes it smooth and time-aware.
> Control makes the physical system execute it.

Once this separation is clear, algorithms like A*, Hybrid A*, RRT, splines, MPC, and Pure Pursuit become tools placed at the correct layer rather than isolated concepts.
