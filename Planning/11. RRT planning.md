# Rapidly Exploring Random Trees: From RRT to RRT* for Sample-Based Robot Path Planning

## 1. Introduction

Path planning is one of the central problems in robotics. A robot must find a valid route from a start configuration to a goal configuration while avoiding obstacles and respecting its motion constraints. In simple two-dimensional grid worlds, algorithms such as Breadth-First Search, Uniform Cost Search, Dijkstra, and A* are often enough. However, many real robotic systems operate in spaces that are too large, continuous, or high-dimensional for full grid discretization to be practical.

A mobile robot moving on a flat floor may only need to plan in:

[
(x, y, \theta)
]

But a robotic arm may have 6 or 7 joints, and a car-like robot may need to consider position, heading, steering constraints, and sometimes velocity. In these cases, discretizing the entire configuration space becomes computationally expensive or even impossible.

This is where **sample-based path planning** becomes important.

Instead of building a complete representation of the entire space, sample-based planners randomly sample configurations and attempt to connect them using a local planner. Two of the most important sample-based methods are:

* **PRM — Probabilistic Roadmap**
* **RRT — Rapidly Exploring Random Tree**

RRT is especially useful because it is a **single-query planner**. It does not try to build a reusable map of the entire configuration space. Instead, it grows a tree specifically for the current start and goal. This makes it faster and more suitable for large or dynamic environments where the planning problem changes frequently. 

---

## 2. From PRM to RRT

### 2.1 PRM: Multi-Query Planning

PRM builds a graph, or roadmap, by randomly sampling many collision-free configurations in the workspace and connecting nearby samples if a local planner can find a collision-free edge between them.

PRM has two phases:

1. **Learning phase**

   * Sample the space.
   * Build a roadmap.
   * Connect nearby nodes.

2. **Query phase**

   * Attach start and goal to the roadmap.
   * Search the roadmap for a path.

This is useful when the environment is mostly static and many queries will be solved using the same graph.

However, PRM has a cost: it spends time building a broad representation of the entire space, even if only one path is needed.

---

### 2.2 RRT: Single-Query Planning

RRT takes a different approach.

Instead of building a reusable roadmap, it grows a tree from the start configuration toward unexplored regions of the space. The goal is not to represent the entire environment. The goal is simply to find one feasible path from start to goal.

This makes RRT:

* Faster for single planning queries
* More directed than PRM
* Better suited for dynamic environments
* Useful in high-dimensional configuration spaces

The trade-off is that the tree is usually not reusable for future planning queries.

---

## 3. Core Concepts of RRT

### 3.1 Configuration Space

A robot’s planning problem is usually defined in **configuration space**, often written as:

[
\mathcal{C}
]

A configuration is a complete description of the robot’s state needed for planning.

For a 2D mobile robot:

[
q = (x, y)
]

or, if orientation is included:

[
q = (x, y, \theta)
]

For a 6-DOF manipulator:

[
q = (\theta_1, \theta_2, \theta_3, \theta_4, \theta_5, \theta_6)
]

The valid space is divided into:

[
\mathcal{C}_{free}
]

and

[
\mathcal{C}_{obs}
]

Where:

* ( \mathcal{C}_{free} ): collision-free configurations
* ( \mathcal{C}_{obs} ): invalid configurations that collide with obstacles

The planner must find a path:

[
\sigma : [0,1] \rightarrow \mathcal{C}_{free}
]

such that:

[
\sigma(0) = q_{start}
]

[
\sigma(1) = q_{goal}
]

---

### 3.2 Tree Structure

RRT builds a **tree**, not a general graph.

A tree has the following properties:

* Each node has one parent.
* There are no cycles.
* There is exactly one path from the root to any node.

In RRT, the root is usually the start configuration:

[
q_{start}
]

Each new node stores a pointer or index to its parent. Once the goal is reached, the final path is reconstructed by walking backward from the goal node to the start node.

---

### 3.3 Random Sampling

At each iteration, RRT samples a random configuration:

[
q_{rand}
]

This sample may be generated uniformly across the space, or it may be biased toward the goal.

Uniform sampling encourages exploration.

Goal-biased sampling encourages faster convergence toward the goal.

A common strategy is:

```text
90% random sampling
10% goal sampling
```

This gives the tree enough randomness to explore while still gently pulling it toward the goal.

---

### 3.4 Nearest Neighbor Search

After generating a random sample, RRT finds the closest node already in the tree:

[
q_{near} = \arg\min_{q_i \in T} |q_i - q_{rand}|
]

Where:

* ( T ): current tree
* ( q_i ): an existing node in the tree
* ( q_{rand} ): random sample
* ( q_{near} ): nearest existing node

This tells the planner where the tree should expand from.

---

### 3.5 Steering

RRT usually does not connect directly to ( q_{rand} ), especially if the sample is far away. Instead, it moves from ( q_{near} ) toward ( q_{rand} ) by a limited distance.

This distance is controlled by the step size:

[
\delta
]

The new configuration is:

[
q_{new} = q_{near} + \delta \cdot \frac{q_{rand} - q_{near}}{|q_{rand} - q_{near}|}
]

If ( q_{rand} ) is closer than ( \delta ), then ( q_{new} ) can simply be ( q_{rand} ).

This steering function controls the growth rate of the tree.

---

## 4. The Basic RRT Algorithm

The basic RRT algorithm can be described as follows:

```text
Initialize tree T
Add q_start to T

For max_iterations:
    Sample q_rand
    Find q_near in T
    Steer from q_near toward q_rand to produce q_new
    If edge(q_near, q_new) is collision-free:
        Add q_new to T with parent q_near
        If q_new is close to q_goal:
            Try to connect q_new to q_goal
            If successful:
                Return path
```

The algorithm is simple, but powerful.

It does not attempt to search every possible state. Instead, it grows a tree that quickly expands into unexplored regions.

---

## 5. Why RRT Explores Rapidly

RRT has an important geometric property: it naturally expands toward unexplored regions.

This happens because nodes on the outer boundary of the tree tend to have larger **Voronoi regions**. A Voronoi region is the area of the space for which a node is the closest existing node.

A node in an unexplored region often owns a large region of space. Therefore, many random samples are likely to select that node as the nearest neighbor. As a result, the tree expands outward quickly.

This is the meaning of “rapidly exploring” in RRT.

---

## 6. RRT-Connect: Growing Two Trees

A common variation of RRT grows two trees:

* One from the start
* One from the goal

This is often called **RRT-Connect**.

The method alternates between growing the two trees. At each step, after adding a new node to one tree, the planner attempts to connect that new node to the other tree.

The simplified logic is:

```text
Initialize tree T_start with q_start
Initialize tree T_goal with q_goal

For max_iterations:
    Grow T_start toward random sample
    Try to connect T_goal to the new node
    Swap T_start and T_goal
```

When the two trees connect, a complete path exists from start to goal.

This method is often much faster than growing only one tree, especially in high-dimensional spaces.

---

## 7. Important RRT Parameters

### 7.1 Step Size ( \delta )

The step size controls how far the tree grows in one expansion.

A small ( \delta ):

* Produces a dense tree
* Captures details better
* Handles narrow passages better
* Increases computation time

A large ( \delta ):

* Expands faster
* Produces fewer nodes
* May skip useful detail
* Increases the chance of collision

Choosing ( \delta ) depends on:

* Map resolution
* Robot size
* Obstacle density
* Required path quality
* Available computation time

For a 2D mobile robot, a practical starting range may be:

```text
0.3 m to 1.0 m
```

But this must be tuned based on the environment.

---

### 7.2 Goal Tolerance

The goal tolerance determines how close the tree must get to the goal before attempting the final connection.

Example:

```text
goal_tolerance = 0.3 m
```

A small tolerance gives a more precise goal connection but may require more iterations.

A large tolerance makes planning easier but may produce a path that does not terminate close enough to the desired goal pose.

---

### 7.3 Maximum Iterations

RRT is not guaranteed to find a solution in a fixed number of iterations.

The maximum iteration count controls how much effort the planner is allowed to spend.

Example:

```text
max_iterations = 5000
```

Increasing this value improves the chance of finding a path but increases planning time.

---

### 7.4 Goal Bias

Goal bias controls how often the planner samples the goal directly.

Example:

```text
goal_bias = 0.1
```

This means:

```text
10% of samples are the goal
90% of samples are random
```

A small amount of goal bias is usually helpful.

Too much goal bias can cause the tree to repeatedly attempt direct growth toward the goal, which may fail in cluttered environments.

---

## 8. Clean C++ RRT Implementation

The following implementation is a clean, educational RRT planner for a 2D occupancy grid. It follows ROS 2-style structure but remains standalone for clarity.

### 8.1 Data Structures

```cpp
struct Point
{
    double x;
    double y;
};

struct Node
{
    Point position;
    int parent_index;
};
```

Each `Point` represents a continuous world position.

Each `Node` stores:

* Its position
* The index of its parent node in the tree

This parent index is what allows the final path to be reconstructed.

---

### 8.2 Planner Class

```cpp
class RRTPlanner
{
public:
    RRTPlanner(
        int width,
        int height,
        double resolution,
        double step_size,
        double goal_tolerance,
        int max_iterations)
        : width_(width),
          height_(height),
          resolution_(resolution),
          step_size_(step_size),
          goal_tolerance_(goal_tolerance),
          max_iterations_(max_iterations),
          rng_(std::random_device{}()),
          x_dist_(0.0, width * resolution),
          y_dist_(0.0, height * resolution)
    {
        grid_.resize(height_, std::vector<int>(width_, 0));
    }
};
```

The planner stores:

* Map width and height
* Map resolution
* RRT step size
* Goal tolerance
* Maximum number of iterations
* Occupancy grid
* Tree nodes
* Random number generator

The map is represented as:

```cpp
std::vector<std::vector<int>> grid_;
```

Where:

```text
0 = free cell
1 = obstacle cell
```

---

### 8.3 Planning Function

```cpp
std::optional<std::vector<Point>> plan(const Point & start, const Point & goal)
{
    tree_.clear();

    tree_.push_back(Node{start, -1});

    for (int i = 0; i < max_iterations_; ++i)
    {
        Point q_rand = sampleRandomPoint(goal);
        int nearest_index = findNearestNode(q_rand);

        Point q_near = tree_[nearest_index].position;
        Point q_new = steer(q_near, q_rand);

        if (!isCollisionFree(q_near, q_new))
        {
            continue;
        }

        tree_.push_back(Node{q_new, nearest_index});
        int new_index = static_cast<int>(tree_.size()) - 1;

        if (distance(q_new, goal) <= goal_tolerance_)
        {
            if (isCollisionFree(q_new, goal))
            {
                tree_.push_back(Node{goal, new_index});
                return reconstructPath(static_cast<int>(tree_.size()) - 1);
            }
        }
    }

    return std::nullopt;
}
```

This function performs the complete RRT planning process.

The start node is inserted first:

```cpp
tree_.push_back(Node{start, -1});
```

The parent of the start node is `-1` because it has no parent.

Each iteration then:

1. Samples a random point.
2. Finds the closest node in the tree.
3. Steers toward the sample.
4. Checks collision.
5. Adds the node if valid.
6. Checks whether the goal can be reached.
7. Reconstructs the path if successful.

If no path is found, the function returns:

```cpp
std::nullopt
```

---

### 8.4 Sampling with Goal Bias

```cpp
Point sampleRandomPoint(const Point & goal)
{
    std::uniform_real_distribution<double> bias_dist(0.0, 1.0);

    if (bias_dist(rng_) < 0.1)
    {
        return goal;
    }

    return Point{x_dist_(rng_), y_dist_(rng_)};
}
```

This introduces a 10% goal bias.

Most of the time, the planner samples randomly. Occasionally, it samples the goal directly.

This makes the tree more likely to grow toward the goal without losing its exploratory behavior.

---

### 8.5 Nearest Neighbor Search

```cpp
int findNearestNode(const Point & q_rand)
{
    int nearest_index = 0;
    double min_distance = distance(tree_[0].position, q_rand);

    for (int i = 1; i < static_cast<int>(tree_.size()); ++i)
    {
        double d = distance(tree_[i].position, q_rand);

        if (d < min_distance)
        {
            min_distance = d;
            nearest_index = i;
        }
    }

    return nearest_index;
}
```

This implementation uses a simple linear scan.

For small educational examples, this is fine.

For production systems, a spatial data structure such as a KD-tree is preferred because nearest-neighbor queries become expensive as the tree grows.

---

### 8.6 Steering Function

```cpp
Point steer(const Point & q_near, const Point & q_rand)
{
    double dx = q_rand.x - q_near.x;
    double dy = q_rand.y - q_near.y;
    double length = std::sqrt(dx * dx + dy * dy);

    if (length <= step_size_)
    {
        return q_rand;
    }

    double scale = step_size_ / length;

    return Point{
        q_near.x + dx * scale,
        q_near.y + dy * scale
    };
}
```

This function limits growth by `step_size_`.

If the random point is close enough, the planner connects directly to it. Otherwise, it creates a new point in the same direction but only one step away.

This is the code form of:

[
q_{new} = q_{near} + \delta \cdot \frac{q_{rand} - q_{near}}{|q_{rand} - q_{near}|}
]

---

### 8.7 Collision Checking

```cpp
bool isCollisionFree(const Point & from, const Point & to)
{
    double dx = to.x - from.x;
    double dy = to.y - from.y;
    double length = std::sqrt(dx * dx + dy * dy);

    int steps = static_cast<int>(length / resolution_);

    for (int i = 0; i <= steps; ++i)
    {
        double t = static_cast<double>(i) / std::max(steps, 1);

        Point p{
            from.x + t * dx,
            from.y + t * dy
        };

        auto [mx, my] = worldToMap(p);

        if (!isInsideMap(mx, my))
        {
            return false;
        }

        if (grid_[my][mx] == 1)
        {
            return false;
        }
    }

    return true;
}
```

Collision checking must validate the **edge**, not only the endpoint.

A common mistake is checking whether ( q_{new} ) is collision-free but ignoring the path between ( q_{near} ) and ( q_{new} ). That can produce invalid paths that pass through obstacles.

This implementation samples points along the edge and checks each corresponding grid cell.

---

### 8.8 Path Reconstruction

```cpp
std::vector<Point> reconstructPath(int goal_index)
{
    std::vector<Point> path;

    int current_index = goal_index;

    while (current_index != -1)
    {
        path.push_back(tree_[current_index].position);
        current_index = tree_[current_index].parent_index;
    }

    std::reverse(path.begin(), path.end());
    return path;
}
```

The path is reconstructed backward:

```text
goal -> parent -> parent -> ... -> start
```

Then it is reversed to produce:

```text
start -> ... -> goal
```

## 9. ROS 2-Style Integration

In a ROS 2 or Nav2-style planner, the RRT planner would usually be wrapped inside a planner plugin.

The planner receives:

```cpp
geometry_msgs::msg::PoseStamped start
geometry_msgs::msg::PoseStamped goal
```

And returns:

```cpp
nav_msgs::msg::Path
```

Conceptually:

```cpp
nav_msgs::msg::Path createPlan(
    const geometry_msgs::msg::PoseStamped & start,
    const geometry_msgs::msg::PoseStamped & goal)
{
    Point start_point{start.pose.position.x, start.pose.position.y};
    Point goal_point{goal.pose.position.x, goal.pose.position.y};

    auto result = rrt_planner_.plan(start_point, goal_point);

    nav_msgs::msg::Path path;
    path.header.frame_id = "map";

    if (!result)
    {
        return path;
    }

    for (const auto & p : *result)
    {
        geometry_msgs::msg::PoseStamped pose;
        pose.header.frame_id = "map";
        pose.pose.position.x = p.x;
        pose.pose.position.y = p.y;
        pose.pose.orientation.w = 1.0;

        path.poses.push_back(pose);
    }

    return path;
}
```

In a real Nav2 plugin, additional work is needed:

* Read the costmap.
* Convert between world coordinates and map indices.
* Check robot footprint, not only point collision.
* Generate valid orientations along the path.
* Smooth the output path.
* Respect planner server interfaces.
* Handle lifecycle configuration and parameter updates.

## 10. Limitations of Basic RRT

Basic RRT is powerful, but it has important limitations.

### 10.1 It Is Not Optimal

RRT is designed to find a feasible path, not the best path.

The first path found is often:

* Long
* Jagged
* Indirect
* Difficult for a controller to follow

This is why post-processing is usually needed.

---

### 10.2 It Struggles in Narrow Passages

Random sampling may have difficulty finding small valid regions, especially when the space contains narrow corridors.

If the probability of sampling inside a narrow passage is low, the planner may need many iterations.

---

### 10.3 It Depends Heavily on Parameters

Bad parameter tuning can make RRT fail or produce poor paths.

For example:

* Step size too small → slow growth
* Step size too large → many collisions
* Goal bias too small → slow convergence
* Goal bias too large → poor exploration
* Too few iterations → no solution

---

### 10.4 It Produces Controller-Unfriendly Paths

Raw RRT paths are usually not smooth.

A mobile robot controller may struggle with sharp turns or irregular waypoint spacing.

Typical post-processing includes:

* Shortcutting
* Spline smoothing
* Collision-aware smoothing
* Orientation assignment
* Velocity profiling

---

## 11. RRT and Non-Holonomic Robots

A holonomic robot can move freely in any direction allowed by its configuration space.

A non-holonomic robot has motion constraints. For example, a car cannot move sideways. Its motion depends on steering angle, turning radius, and sometimes speed.

RRT can support non-holonomic systems because the steering step does not have to be a straight line. Instead, the local planner can use a motion model.

For a car-like robot, the local planner may use:

* Dubins curves
* Reeds-Shepp curves
* Bicycle model integration
* Kinodynamic rollout

This is one reason RRT is useful for robotics and autonomous driving.

Instead of connecting two points with a straight line, the planner connects configurations using feasible vehicle motions.

---

## 12. From RRT to RRT*

Basic RRT is fast, but it does not optimize the path.

RRT* modifies RRT to improve path quality over time.

The key difference is:

```text
RRT finds a feasible path.
RRT* keeps improving the path.
```

RRT* is **asymptotically optimal**, meaning that as the number of samples approaches infinity, the solution cost approaches the optimal cost.

Formally:

[
\lim_{n \to \infty} cost(\sigma_n) = cost(\sigma^*)
]

Where:

* ( \sigma_n ): best path found after ( n ) samples
* ( \sigma^* ): optimal path
* ( cost(\sigma^*) ): optimal path cost

---

## 13. RRT* Optimization Logic

RRT* adds two major ideas:

1. **Choose the best parent**
2. **Rewire nearby nodes**

These two changes transform RRT from a pure exploration algorithm into an incremental optimization algorithm.

---

### 13.1 Nearby Node Set

Instead of connecting only to the nearest node, RRT* finds a set of nearby nodes:

[
X_{near} = {x_i \in T \mid |x_i - x_{new}| \leq r(n)}
]

Where:

* ( X_{near} ): nearby nodes
* ( T ): current tree
* ( n ): number of nodes
* ( r(n) ): search radius

A common radius form is:

[
r(n) = \gamma \left(\frac{\log n}{n}\right)^{1/d}
]

Where:

* ( \gamma ): tuning constant
* ( n ): number of nodes
* ( d ): dimension of the configuration space

The radius shrinks as the tree grows.

Early in planning, the radius is larger, allowing broad improvement. Later, the radius becomes smaller, making optimization more local and efficient.

---

### 13.2 Cost-to-Come

Each node stores a cost from the start:

[
J(x)
]

For simple geometric planning, the edge cost is usually Euclidean distance:

[
c(x_i, x_j) = |x_j - x_i|
]

Then the cost of reaching a new node through a candidate parent is:

[
J(x_i) + c(x_i, x_{new})
]

---

### 13.3 Choosing the Best Parent

Basic RRT connects ( x_{new} ) to the nearest node.

RRT* checks all nearby nodes and chooses the parent that gives the lowest total cost:

[
x_{parent} =
\arg\min_{x_i \in X_{near}}
\left(
J(x_i) + c(x_i, x_{new})
\right)
]

Subject to:

[
edge(x_i, x_{new}) \subset \mathcal{C}_{free}
]

So the selected parent must satisfy two conditions:

1. It gives the lowest path cost.
2. The edge to the new node is collision-free.

This is the first optimization step.

---

### 13.4 Rewiring Nearby Nodes

After inserting ( x_{new} ), RRT* checks whether the new node can improve the cost of nearby existing nodes.

For each nearby node ( x_i ), the planner checks:

[
J(x_{new}) + c(x_{new}, x_i) < J(x_i)
]

If true, and the edge is collision-free, then ( x_i ) is rewired:

```text
old parent of x_i is removed
x_new becomes the new parent of x_i
cost of x_i is updated
costs of descendants are updated
```

This is the second and most important optimization step.

The tree is not only growing. It is improving its own structure.

---

## 14. RRT* Algorithm

The RRT* algorithm can be written as:

```text
Initialize tree T with x_start

For max_iterations:
    x_rand = sample()
    x_nearest = nearest(T, x_rand)
    x_new = steer(x_nearest, x_rand)

    If edge(x_nearest, x_new) is not collision-free:
        continue

    X_near = near(T, x_new, r(n))

    x_best = x_nearest
    best_cost = J(x_nearest) + c(x_nearest, x_new)

    For each x_i in X_near:
        If edge(x_i, x_new) is collision-free:
            candidate_cost = J(x_i) + c(x_i, x_new)
            If candidate_cost < best_cost:
                x_best = x_i
                best_cost = candidate_cost

    Add x_new with parent x_best and cost best_cost

    For each x_i in X_near:
        If edge(x_new, x_i) is collision-free:
            candidate_cost = J(x_new) + c(x_new, x_i)
            If candidate_cost < J(x_i):
                Rewire x_i through x_new
                Update descendant costs

Return best path to goal
```

## 15. RRT vs RRT*

| Feature          |              RRT |                    RRT* |
| ---------------- | ---------------: | ----------------------: |
| Main goal        |    Feasible path |          Optimized path |
| Parent selection |     Nearest node | Lowest-cost nearby node |
| Rewiring         |               No |                     Yes |
| Path quality     |     Usually poor |      Improves over time |
| Runtime          |           Faster |                  Slower |
| Optimality       |      Not optimal |  Asymptotically optimal |
| Best use         | Fast feasibility |   High-quality planning |

## 16. Practical Engineering Insights

### 16.1 RRT Is Good for Finding a Path Quickly

RRT is useful when the most important question is:

```text
Can I reach the goal?
```

It is often a good choice when:

* The space is high-dimensional.
* The environment changes often.
* A quick feasible path is more important than optimality.
* The planner will be followed by smoothing and control.

---

### 16.2 RRT* Is Better When Path Quality Matters

RRT* is useful when the question becomes:

```text
What is the best path I can find with the available computation time?
```

It is better when:

* Shorter paths matter.
* Energy consumption matters.
* Smoothness matters.
* There is time to improve the solution.

However, RRT* is more expensive than RRT because it performs nearby searches and rewiring.

---

### 16.3 Basic RRT/RRT* Is Still Not Enough for Cars

For autonomous vehicles and car-like robots, straight-line steering is usually invalid.

A car-like robot needs constraints such as:

* Minimum turning radius
* Forward/reverse motion limits
* Curvature limits
* Velocity and acceleration constraints

For these systems, RRT or RRT* must be combined with a proper local planner.

Common choices include:

* Dubins steering
* Reeds-Shepp steering
* Kinodynamic RRT
* Hybrid A*
* State lattice planning

---

### 16.4 Collision Checking Should Use the Robot Footprint

Educational examples often check a point robot.

Real robots have size.

Instead of checking only:

```text
Is this point inside an obstacle?
```

A real planner must check:

```text
Does the robot footprint collide at this pose?
```

This means checking the robot’s body shape against the costmap.

For mobile robots, this usually involves:

* Circular footprint
* Polygon footprint
* Inflation radius
* Costmap collision checker

---

### 16.5 Path Smoothing Is Usually Required

The raw output of RRT is rarely ready for execution.

A typical pipeline is:

```text
RRT / RRT*
    ↓
Path shortcutting
    ↓
Spline smoothing
    ↓
Orientation generation
    ↓
Velocity profiling
    ↓
Controller execution
```

Without smoothing, the robot may receive sharp, irregular waypoints that are difficult to track.

---

## 17. Common Failure Cases

### 17.1 No Path Found

Possible causes:

* Too few iterations
* Step size too large
* Step size too small
* Start or goal inside obstacle
* Collision checker too strict
* Narrow passage not sampled

---

### 17.2 Path Passes Through Obstacles

Possible causes:

* Only node collision was checked
* Edge collision checking resolution is too low
* Robot footprint was ignored
* Map/world coordinate conversion is incorrect

---

### 17.3 Planner Is Too Slow

Possible causes:

* Linear nearest-neighbor search with many nodes
* Too many collision checks
* Very small step size
* Large number of iterations
* RRT* rewiring radius too large

Possible improvements:

* Use KD-tree nearest-neighbor search
* Tune step size
* Reduce goal bias if it causes repeated failed extensions
* Use informed sampling after finding first solution
* Limit rewiring radius

### 17.4 Poor Path Quality

Possible causes:

* Basic RRT instead of RRT*
* No smoothing
* Large step size
* Weak cost function
* No curvature constraints

Possible improvements:

* Use RRT*
* Apply shortcut smoothing
* Add curvature-aware local planner
* Use Dubins/Reeds-Shepp connection
* Use Hybrid A* or state lattice planning for car-like robots

## 18. Conclusion

RRT is one of the most important sample-based planning algorithms in robotics because it can solve problems that are difficult for traditional grid-based search methods. Instead of discretizing the entire configuration space, it grows a tree from the start configuration toward randomly sampled points. This allows it to explore large and high-dimensional spaces efficiently.

The key ideas behind RRT are:

* Random sampling
* Nearest-neighbor search
* Steering with a limited step size
* Collision checking
* Parent-based path reconstruction

Basic RRT is fast and effective for finding feasible paths, but it does not optimize path quality. RRT* improves RRT by choosing the best parent for each new node and rewiring nearby nodes when a cheaper path is found. This makes RRT* asymptotically optimal, but also more computationally expensive.

For real robotic systems, RRT and RRT* are usually only part of the full planning pipeline. A practical planner must also consider robot footprint, map resolution, motion constraints, smoothing, and controller compatibility.

The engineering takeaway is simple:

```text
RRT is excellent for fast feasibility.
RRT* is better for path optimization.
Both need proper collision checking, tuning, and smoothing before real robot deployment.
```
